# gr0wthlab agent memory

gr0wthlab is the Marketing Engineer's repository; [`README.md`](README.md) gives the purpose, actors, weekly cycle, Guardrails, and layout.

- Use the vocabulary in [`CONTEXT.md`](CONTEXT.md): capitalized terms (Founder, Product, Draft, Evidence, Go-To-Market Package, Review Queue, and the rest) carry only the senses defined there.
- [ADR 0001](docs/adr/0001-evidence-and-drafts-only.md) is the founding boundary: this repository holds Evidence, Drafts, and Review Queue items, never strategy; Go-To-Market Packages stay in Mandu, and Product changes go to firstmate as Dispatches.
- [ADR 0002](docs/adr/0002-the-founder-decides-in-gr0wthlab.md): the Founder decides here, not in Mandu.
  The Founder's decisions and the records of what the Founder did live in `ledger/founder/`, and [`src/gr0wthlab/founder.py`](src/gr0wthlab/founder.py) is the one place that states and enforces who writes them and what is ever read as one.
  Only `src/bin/gr0wthlab sitting` writes there, on the Founder's own act on its page: `sitting.py` is the only maker of `founder.Writer`, a run only reads, the launcher's `Store` refuses every path there, and nothing under `workspace/` is ever read as a Founder record, through a link or otherwise.
  Each of the six record folders is a forbidden target of the preflight before every session and of the boundary check, so a folder is added only together with its target.
  A decision can be changed or taken back on the page until a run has taken it in, which is when its Evidence in `ledger/evidence/decisions/` exists, and never after; the page and the run hold `founder.locked` around the two.
  The page (`page.py`, `serve.py`, `src/sitting/`) shows everything an item, a run report, or a record says as text, through `page.tag`; it answers on the loopback address behind a secret that is new each start, and takes a change only as a POST from its own form, with `Host` and `Origin` checked.
  It is standard library only, starts no process, opens no connection, and calls no model; `src/tests/test_founder.py`, `test_page.py`, `test_sitting.py`, and `test_serve.py` hold each of these, and a change to the page is also driven in a real browser, which sends what no unit test's request does.
  A run knows a sitting took place from its sitting record, which the page's last view writes as its one way to finish before it stops, or from the `sitting` date of a decision given at it, and marks what that sitting left undecided as carried over; nothing else is read as the sign of a sitting.
  A sitting known from a decision alone has no time: its Evidence keeps `minutes` as null, and nothing counts it as zero.
  A sitting that left neither leaves no mark: its undecided items come back without the carried-over mark, nothing records its time, the run report has no line for it, and nothing saved at it is lost.
  gr0wthlab reads nothing from Mandu but the Go-To-Market Package: `mandu.exchange` and `GR0WTHLAB_EXCHANGE_DIR` are gone and are no longer read.
- [ADR 0004](docs/adr/0004-posting-is-manual.md) and [ADR 0005](docs/adr/0005-the-weekly-read-uses-no-youtube-connection.md): the Founder posts by hand, and gr0wthlab reads no platform and holds no credential, so the run report lists the scheduling service as not used (`sources_not_used` in `config/run.json`), never as failed.
  The Founder types each number the Weekly Read asks for on the sitting page, and the page keeps no screenshot or file ([ADR 0006](docs/adr/0006-the-founder-types-the-weekly-read-numbers.md), the Founder's decision of 2026-10-14).
  In a read week the Founder gives each post's numbers on the sitting page, read from TikTok Studio or YouTube Studio (`founder/results/`): `results.py` works out from the kit exactly what to ask (each post on the platform that judges it: its views for the floor, what the signals and kill criteria of the read's posts on that platform name, since each post is ranked against the others there, and its comments) and takes each record in as Evidence for that post, and `weekly_read.py` holds the agent's memo to the checks the launcher can make without restating `read-the-results.md` and queues one Weekly Read decision item for each line; nothing else queues one (`queue.FROM_DRAFT`).
  A number not given is not reported, never zero, and a post with nothing given is never taken to be not posted; the floor counts each platform's views (the Founder's decision of 2026-10-14), and the launcher reads only the floor's figure from `read-the-results.md`.
- [The v1 PRD](docs/prd/prd-marketing-engineer-v1_261008.md) is the story tracker: when a story lands and its Validation Test passes, flip that story's acceptance-criteria checkboxes and no others.
- `workspace/` is the agent's only writable tree (Guardrail G1); code in `src/`, configuration in `config/` (Guardrails, the Product registry, and the run settings), and docs change only through firstmate's reviewed pull requests (G8).
  Keep that split when adding files: the Codex permission profile in [`config/guardrails/runtime.json`](config/guardrails/runtime.json) makes exactly the six `workspace/` areas writable, and the launcher's own records go in `ledger/`, which a run can read and never write; the Founder's records are in `ledger/founder/`, which the launcher never writes either.
- Every run starts through `src/bin/gr0wthlab`; the [US-ME02 spike note](docs/spikes/us-me02-runtime-boundary.md) explains the boundary.
  A change to the launcher, `runtime.json`, `fetch.json`, or `products.json` needs a fresh `src/bin/gr0wthlab boundary-check` on the Founder's Mac, which CI cannot run.
  That check (`src/gr0wthlab/probe.py`) proves each forbidden target, a write or a read, on its own from the runtime's records, Codex's record of each tool call (kept under `codex.LOG_FILTER`) and the kernel's log, never from a count or the agent's report; a change may make the probe easier for the agent to carry out, never the proof looser.
  Every line it prints, and every sentence the docs say about its output, states only what a record shows and names no cause beyond it.
  The preflight before each session is held to the same: its footage and network probes say the sandbox could read or reach something only with a listing or a connection on the probe's own output, and one that fell short without either says the check did not finish (`footage_reason` and `network_reason` in `src/gr0wthlab/launcher.py`, the one wording a session's record, the run report, and the notice carry), and the run report's `Sandbox footage` and `Sandbox network` lines count a session as tried only where its own record leaves no target untried (`report.probe_scope`).
- A run is `src/gr0wthlab/cycle.py` around one sandboxed agent session for each workflow that has work due: deterministic work (snapshot, decisions, item validation, queue order, report, git records) is launcher code with unit tests, judgment is the agent's under the fixed task definitions in `src/instructions/weekly-run/`, and [operations](docs/operations.md) covers the production clone and schedule.
  `src/gr0wthlab/sessions.py` fixes the sessions' order and puts each task definition together from the part every session shares, the shared parts a workflow uses, and the workflow's own part: write a rule that binds every session in `common.md` alone, and `src/tests/test_sessions.py` holds that every definition carries it.
  A workflow with nothing due starts no session; every session starts with the same command, proved against the boundary first, and only the files in `workspace/` pass from one to the next.
  The launcher takes nothing in while a session can still write: every take-in runs once, after the last session, by the rules it had when a run was one session.
  One session's trouble (not started, stopped at its limit, an error) always marks its own workflow's outputs incomplete with the real reason, and only those, and the sessions after it still run ([operations](docs/operations.md#one-session-per-workflow)).
  Starting and marking are one test, `Cycle.nothing_due`: a session is due exactly when its workflow owes work the launcher can name, and every workflow's gap rule puts the gap of a due session that fell short in that workflow's own output, whatever the session had written by then; a new workflow's gap rule must do the same, and `FullWeekTest` in `src/tests/test_sessions.py` holds it for all of them.
  The agent adds Review Queue items only through `workspace/review-queue/incoming/`, never a post or a message, which the launcher renders only from a checked Draft (`FROM_DRAFT` in `src/gr0wthlab/queue.py`); the launcher publishes them into `ledger/`, where it alone writes the queue, its own Evidence, run reports, and per-workflow run state.
  Run state (`src/gr0wthlab/state.py`) is a convenience validated every run: the Review Queue and the Founder's decision records stay the source of truth.
- A read that cannot be made never withdraws, closes, or supersedes an open item: only what a record the launcher could read says does.
  Where a failed read would otherwise have taken an open item back or asked it again, the place weighs it through `queue.stands` in `src/gr0wthlab/queue.py`: the item stays as it is under its identifier, the workflow reports the read as its gap with the real reason, and `cycle.left_standing` puts the item in the run's notice.
  Those places judge an open item: the check of an open post, message, reply, or recruiting item against its Draft and what that check reads, an open invitation or Waitlist ask while a report of the Founder's is unread, an open follow-up whose record of the first message is unread, the open filming plan while the kit is unread, a Dispatch request's open item whose item file is unread, and an item in `incoming/` that supersedes an open item whose item file is unread.
  Where a whole step did not run because its source could not be read, it judges no item: the output always reads incomplete in the run report with the real reason, and no item of that step is touched or listed.
  Those are recruiting without a usable Waitlist view or Beta Build record, a Dispatch request whose reviewed text is unread, post Drafts without the calendar, outreach without the channel plan or the kit, replies without the kit, and the video of a day whose copy is approved and whose Draft is unread.
  The notice names such a source only where its read failed as a source (a package file the snapshot could not read, the Waitlist view, the Beta Build record), where it was read and could not be used, or was recorded as a launcher problem (a reviewed Dispatch text, a kit that could not be prepared), and in the line that says no video was cut for an approved day.
  A package file the snapshot read that launcher code then could not parse or decode, such as a calendar that lost its table or a channel plan that is not UTF-8, is a failed source like an unread one: `Cycle.unusable_sources` marks its one line `unusable` with the reason before the first session, and a new launcher read of a package file reports to it the same way; `Cycle.outputs` then names on that line exactly the outputs whose rows carry a gap naming the file, never the package snapshot or review, so the notice and the report agree.
  While the window's filming plan is open, that plan also stands on a kit file that fails this way, so the notice's list of open items not checked again names the plan with the kit file as its reason.
  A new place that takes an open item back must list every read its decision rests on and route each through `queue.stands`, with one test that the item stands (`assert_stands` and `assert_never_asked_again` in `src/tests/test_cycle.py`) and one that a real withdrawal still happens; [operations](docs/operations.md) says which reads each workflow counts.
  Where it meets the video-file check below, the unread source decides for that run: a post whose finished file is gone gives way only once its Draft can be read and checked.
  A failed read asks nothing decided again either: a Dispatch request is held while neither a rejected item's file nor the run state's fingerprint of it shows what the Founder rejected (`dispatch.rejected_text`), and an item in `incoming/` is set aside while it has the kind and ask of a queued item known by neither (`queue.may_repeat`).
  Known gap, not yet decided by the Founder: a proposed Angle (`listening.take_proposals`), a reviewed proposal (`proposals.file_once`), and a Dispatch request that an item of another origin already asks (the `ASKED` stop in `dispatch.file`) still compare by known fingerprints alone, so each can repeat a decided item whose file and fingerprint are both lost.
- Every run ends with its report (US-ME17), so nothing the launcher waits for may wait forever: start a process only through `src/gr0wthlab/process.py`, which gives it a time limit and stops it with every process the process table shows it started; `src/tests/test_process.py` watches a whole run and fails when a process it starts does not go through `process.run` or is waited on without a time limit.
  Every session's limit is `agent.time_limit_seconds` in `config/run.json`, counted for that session alone, all of a run's sessions together are bounded by `agent.run_time_limit_seconds`, and [operations](docs/operations.md#when-a-session-times-out) says what a timed-out session leaves.
  A network read is bounded the same way: `fetch.send` ends each wait at `timeout_seconds` and each whole read at `read_deadline_seconds`, both in `config/guardrails/fetch.json`.
- Nothing holds the Mac awake, wakes it, or schedules a wake (the Founder's decision of 2026-10-11; `src/tests/test_attempts.py` watches every process a scheduled run starts and every LaunchAgent key): each week's run happens when the Mac is awake.
  A start of the weekly schedule is first the owed-run check in `src/gr0wthlab/attempts.py`, which begins a run only while `ledger/run-reports/attempts/` shows the week's run still owed and the Mac is fully awake, not in a dark wake; a one-off start (`--once`) always runs, as a run on demand does, and is never an attempt.
  Only an attempt that did not complete and that the Mac slept during, anywhere from its start to its last session's end, earns another, within `schedule.attempts_per_week`, and it is a fresh, whole run that starts every session again; an attempt the Mac slept during completed only if every session ended without an error and confirmed its work.
  [Operations](docs/operations.md#a-run-happens-when-the-mac-is-awake) has the rules, and a change to the schedule's day, time, or check interval in `config/run.json` needs the LaunchAgent installed again.
- A session's closing `Session:` line is the agent's own word, and such a line has read complete after the shallowest sessions: judge a run, and any change to the agent's settings or a task definition, by what the launcher counts of each session (`src/gr0wthlab/work.py`, shown in the run report's Sessions section beside that line; [operations](docs/operations.md#reading-each-sessions-work)).
  Those counts are of one session alone, inform the Founder, and never gate; the launcher reads a closing line only for the package review's output and for a weekly attempt the Mac slept during.
  The agent's reasoning effort is `codex.reasoning_effort` in `runtime.json`, and more wording in the task definition did not stop a session ending early.
- Guardrail G6 lives in launcher code: only `src/gr0wthlab/waitlist.py` reads RepToday's anonymous Waitlist view, from a path outside everything the sandbox reads, checks every value for an email address before anything else, and keeps entry identifiers and counts only; never route the view, or anything else read from it, to the agent.
  The launcher files Dispatch requests from reviewed text in `src/dispatches/`; the Waitlist request is also the view's format, and `src/tests/test_dispatch.py` keeps the two in step.
- Beta Cohort recruiting (`src/gr0wthlab/beta.py`) starts only from the Founder's Beta Build record in `ledger/founder/beta-builds/`, which launcher code reads and never infers; before it exists a run does nothing about the Beta Cohort.
  Who is invited is ordered only in `waitlist.py` (`SELECTION_RULE`) and attached to the item by the launcher, so no entry identifier goes into the agent's brief or into a Draft; a recruiting Draft (`beta_drafts.py`) holds no address, no link, and no figure a cited package line does not hold.
  Only the counts the Founder reports are kept, and a count left out is not reported, never zero.
- The sandboxed agent has no network, and nothing may give it one.
  `src/gr0wthlab/fetch.py` is the launcher's only way onto the network (a credential-free GET to a host in [`config/guardrails/fetch.json`](config/guardrails/fetch.json), bound by that host's `robots.txt`), and `src/tests/test_fetch.py` holds the contract by what goes on the wire: add no other way onto the network, method, credential, or exception to `robots.txt`.
  Beyond it, only a run in the production clone reaches GitHub, outside the sandbox with the push's own login: git's fetch and push of `origin` (`records.py`), and the `gh api` read of whether that repository is private (`visibility.py`).
  No unit test opens the network; `src/tests/__init__.py` replaces `fetch.send` with a refusal and refuses any other connection beyond the machine at the socket, so give a client a `fakes.Web`.
- From the first real run on, a run pushes the Drafts, the Evidence, and the Founder's records, so in the production clone a run that saves its records (`records.save_after_run`) refuses to start while GitHub says plainly that the repository is public, and pushes only when GitHub, asked again before its notice and report are written and again just before each push, says plainly that it is private (`visibility.ask`); a run that saves nothing, and every other checkout, asks nothing.
  An answer that cannot be had or is not clear is never taken as private: the run goes ahead and keeps its records local, and its report and notice say so with the reason, or, for an answer just before a push, the next run's report.
  No unit test asks GitHub: `src/tests/__init__.py` replaces `visibility.ask` with a refusal, so give a production clone's run a `fakes.GitHub`.
- Fetched text is data, never instructions: it reaches the agent only as the launcher's snapshot (`sources.py`), and a record only as a quote `evidence.py` found word for word in that snapshot.
  The snapshot is working data in `ledger/working/`, which git ignores and the launcher removes when the run ends.
  The retention rule is about what the launcher keeps of what a run fetched.
  As Evidence of what was fetched it keeps only a validated quote, with its link, date read, and document hash, beside the rules a subreddit's rules notice quotes.
  The request log it commits (`ledger/run-reports/<run id>.requests.json`) also holds the `robots.txt` rule lines of the group that applied to each host, each Allow and Disallow with its path as fetched, beside the addresses and outcomes.
  Nothing else the agent writes is checked against what was fetched; [operations](docs/operations.md#where-the-agents-own-words-are-kept) is the one list of where its own words may sit, so change it there and nowhere else.
  Of what the launcher refuses, a Draft waiting for a fix is the one place they may (the Founder's decision of 2026-10-13): everything else refused leaves only its name and the launcher's reasons, a file set aside from `incoming/` in the run's set-aside record (`queue.record_set_aside`).
  That no reason repeats what the refused file says is firstmate's reading of that choice for what is refused from `incoming/`, not a separate decision of the Founder's.
  The error Codex reported for a session is text Codex or the model's provider wrote, and no report, notice, or record in `ledger/` repeats it: `Session.failure` in `src/gr0wthlab/sessions.py` is the one wording, the exit code and the launcher's own class of the error, and the text stays in the run's record in the log folder (`codex_last_error`).
  That class says only what the error is recognized as, never what the agent did before it.
  The reason a session did not start is the launcher's own, and after a `codex --version` or `codex sandbox` probe that exited with an error it ends with up to 500 characters of what that probe wrote to its error stream; those probes run with no model.
  An item marks any text a third party wrote with `exchange.third_party`, the one marking [`docs/mandu-exchange.md`](docs/mandu-exchange.md) tells Mandu's side is data.
  The agent's work in Listening and outreach is taken in the same way as a post Draft: a quote, a proposed Angle or Hook, and a message each become a record or an item only through `listening.py`, `outreach.py`, and `messages.py`.
  Every package-change proposal declares `new_angle`: one that declares `yes`, since it adds or changes an Angle or Hook (FR-7), is queued only when its Evidence names a kept quote's record exactly (`queue.declaration_problem`), and one that declares `no` is queued whatever it touches or says.
  No wording check stands behind a declaration: it is shown on the item, and the Founder is the check on a wrong one.
- The rejection codes and their execution-versus-strategy split live in `src/gr0wthlab/learning.py`.
  The Instructions in force are `ledger/instructions/`, which the sandbox reads and never writes, and `workspace/instructions/` holds only the one change the rejection reasons' session may propose ([ADR 0003](docs/adr/0003-instructions-change-only-through-their-example-set.md)); `ledger/instructions/` and `src/examples/` are each a forbidden target of the preflight and of the boundary check (`instructions-in-force`, `example-sets`).
  `learning.put_back` restores both after every session, in the step of `Cycle.run_sessions` that restores access to `workspace/`, keeping only that session's proposal; keep that the one place they are put back.
- A proposed Instructions change is kept only in `Cycle.learn`: `instructions.py` refuses it unless it cites offered execution reasons alone (a strategy reason never) and adds no package text, and `examples.py` re-runs the workflow's example set, each example as that workflow's own session in a lab under `ledger/working/examples/` (`Cycle(only=...)`), with the text in force and with the proposal; it is kept only when no deterministic assertion that held with the text in force fails with the proposal and holds again when the text in force is run again, at most one change per run, bounded by `learning` in `config/run.json`.
  Judged statements are judged by nothing, by the Founder's decision of 2026-10-14, and rejecting a kept change's notice undoes it at the next run.
  Every example the agent re-runs must hold in `src/tests/test_example_runs.py` with a stand-in that writes a good output.
- [`docs/mandu-exchange.md`](docs/mandu-exchange.md) is the versioned contract for every record's format and for what Mandu, a reader, may do with them; Mandu's read-only side, Mandu's gr0wthlab-reader skill, is built in Mandu through firstmate from it, and a format change takes a new version there.
- A post item exists only as the launcher's rendering of a Draft in `workspace/drafts/posts/` that passed every check in `src/gr0wthlab/drafts.py` (driven by `posts.py`); the brand lint's only rule source is Mandu's `brand-rules.json`, so a word list changes through a package-change proposal (`src/proposals/`), never in gr0wthlab, and platform facts live in `config/platforms.json`.
- Of Mandu the sandbox reads only the package paths the Product registry names (`boundary.package_paths`), never the checkout as a whole: name a new package file in the registry, and add no grant that covers more of Mandu.
- Filming (US-ME09) keeps the Founder's raw footage private and whole: only the launcher reads the footage folders, the `window-<n>/` folders of the footage place (`filming.footage` in `config/products.json`, RepToday's own folder in Mandu, beside its package), and nothing in gr0wthlab writes, renames, or deletes there.
  `boundary.keep_footage_unread` is the one place the rule is kept that no grant covers a footage folder or lies in one; the preflight shows the sandbox refused a listing of each before every session's agent starts, and the boundary check has the agent try.
  Keep the sandbox out by granting less, never with a deny entry: Codex tells the agent what a profile denies, and an agent told so did not attempt the read, so the check could not prove it ([what was measured](docs/live-checks/20261012-gr0wthlab-footage-place.md#the-route-chosen)).
  The launcher files the filming plan from the kit (`shots.py`, `filming.py`) and renders finished video with ffmpeg (`video.py`) into `ledger/assets/`, which never enters git; the agent, which cannot watch video, only writes edit records in `workspace/drafts/edits/` (`edits.py` checks them).
  One rule covers an A/B pair's videos: when a run ends, the pair's two posts never both show a video unless the two show the same source ranges outside each one's opening.
  `Filming.pair_check` keeps it once per pair, on the videos' own asset records, after `posts.take` has settled every day and before it queues any; keep it the only place a leg is judged by its other leg's video.
  The launcher never says a post shows or keeps a video unless the finished file is on disk and is the file its record and the post's entry name: `filming.on_disk` is the one check, so call it and never read `asset_sha256` alone to make that claim; a file that cannot be read is not a file that is gone, and an open post whose file is gone or changed, in a run that cannot cut the video again, gives way to the same post with no video (`posts.settle_day`, the Founder's decision of 2026-10-12) unless a standing rule has it stand or leave the queue instead ([operations](docs/operations.md#video-tooling-and-finished-videos) lists them).
  Tests that need the real ffmpeg skip with a reason where it is absent; the fake tooling in `src/tests/fakes.py` covers whole runs everywhere.
- Each workflow ships an example set in `src/examples/<workflow>/evals.json` built on synthetic fixtures, never a Product's package; its deterministic assertions run in the unit tests, and adapted third-party text is listed in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).
- Code runs under the Mac's `/usr/bin/python3` (3.9), standard library only; [the CI workflow](.github/workflows/ci.yml) defines the tests and lint every change must pass.
- A change records its live checks (the re-check after it, timed runs, what was not exercised) in a new file of its own, named and written as [`docs/live-checks/README.md`](docs/live-checks/README.md) says, and never adds them to a document another change edits; the US-ME02 spike note keeps the history up to 2026-10-12.
- No reference copy of any Go-To-Market Package lives in this repository: configuration, the Product registry ([`config/products.json`](config/products.json)), and Instructions point to Mandu instead of restating package content.
  A record (Draft, proposal, Evidence, memo) may quote only the specific package text it uses or proposes, citing its Mandu source.
  The specification and decision records under `docs/` (including `docs/prd/design-decisions-2026-10-08.md`) and `CONTEXT.md` are committed as written.

## Maintaining this file

Keep this file for knowledge useful to almost every future agent session in this project.
Do not repeat what the codebase already shows; point to the authoritative file or command instead.
Prefer rewriting or pruning existing entries over appending new ones.
When updating this file, preserve this bar for all agents and keep entries concise.
